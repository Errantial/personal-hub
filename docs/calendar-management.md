# Selected Calendar changes

Implemented 2026-10-12. `POST /api/v1/calendar/batch` applies one atomic action to 1-100 explicit owned calendar records. UI controls and offline replay remain pending. These are local planner records; read-only imported calendar entries and real provider calendars are not writable through this route.

## Contract

`calendarBatchRequestSchema` requires `operationId`, distinct `{id,expectedVersion}` selections and one action:

- `{kind:delete}` tombstones entire selected calendar records, including all-day and recurring series.
- `{kind:study-status,status:planned|completed|cancelled}` changes only one-time timed study blocks with active class/topic ancestors.

Ordinary commitments, all-day items and recurring series are rejected as a whole for study-status changes with `CALENDAR_STUDY_SELECTION_REQUIRED`. Individual occurrence editing retains its existing endpoint; batch status never ambiguously completes every occurrence of a series. Deletion is explicitly at the record/series level, not the clicked occurrence level.

`calendarBatchResponseSchema` returns `events` in selection order. Every selected record advances its version once. The owner schedule lock, canonical ancestor/event locks, all-record validation and mutation receipt make the operation atomic. Missing/foreign/deleted selections return 404; stale versions return `VERSION_CONFLICT`. Historical deletion is allowed for archived-class records; status editing still requires active ancestors. Session authorization is checked for fresh changes and historical receipt replay.

## Behavior to preserve

Only study status or deletion/version timestamps change. Titles, notes, times, timezone, recurrence, exceptions, class/topic identity, source snapshots and captured labels are preserved. Unknown legacy academic history remains unknown and AI-blocked; marking study complete does not certify provenance. Study completion does not submit an assignment, erase its estimate/score or infer mastery.

No email, invitation, notification or provider request is generated by the batch. Reminder delivery separately rechecks availability under the schedule lock; completed/cancelled/deleted targets suppress pending delivery. Existing delivered notification history remains. Returning a block to planned or restoring it individually never restarts jobs already cancelled by delivery checks; new reminders require deliberate scheduling. Individual restore retains recurrence/source history.

Retry an exact request/operation after a lost response. Changed reuse returns `OPERATION_CONFLICT`. A historical retry does not reapply status/deletion after later edits or restore; reload current records before displaying it as current. Failed validation or SQL writes roll back all events, schedule revision and receipt.

## Verification and limits

Synthetic tests cover bounded/strict actions, mixed selection rejection, ownership/origin/session checks, stale versions, archived ancestors, input ordering/case normalization, source/label preservation, SQL rollback, concurrent/duplicate requests, claimed reminder suppression, recurrence exceptions, export, individual restore and persisted restart. Disposable PostgreSQL coverage includes duplicate status batches and overlapping deletion races; it remains opt-in locally.

No migration/dependency, native/offline controls, filter-wide selection, batch restore, automatic rescheduling or external calendar write is added. UI review must explain whole-series deletion and preserve pending/error/conflict states. Invitations and cancellation emails still require the separate explicit email approval path; calendar authority proves no provider capability.

Final validation: all 12 Calendar-management tests and three shared batch-authorization tests pass, including final receipt reauthorization. `npm run check` passed 505 API/client tests with one optional PostgreSQL skip, lint, types, formatting and builds. All 84 browser regressions passed on an isolated rerun; compiled API smoke verified the endpoint and retry wiring with all 45 migrations and zero network calls. UI/offline controls and standard PostgreSQL verification remain pending.
