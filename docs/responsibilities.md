# Responsibility records, review schedules and activity

Three legacy milestones implemented 2026-10-11: owned lifecycle (034), UTC review schedules/due admission (035), and blocked run/activity history/export (036). Responsibilities without a template remain owner-invoked blocked placeholders, with no model/tool execution. D57 adds the agent path below; full Dots/OpenDots parity remains future scope.

Persistent agents (D57, 2026-10-14, [design](superpowers/specs/2026-10-14-persistent-agents-design.md)): a responsibility with a `template` is an agent. It has a pinned Assistant conversation, a local schedule (up to six daily times) and a monthly cap. Its admitted runs are `queued` and executed by the in-process agent worker (queued → running → completed/failed, 10-minute lease, one at a time). Responsibilities without a template are unchanged: owner-invoked, `blocked`, never executed. Agents are created and edited through `/api/v1/agents`; pause, resume and delete use the endpoints below. Resume starts at the next future slot, and delete unpins and keeps the conversation. The design's out-of-scope list still applies.

## Milestone 1: owned responsibility lifecycle

D57 UI is deployed in release `519054d` (2026-10-14; live owner acceptance pending): pinned Assistant conversations, create/edit, Pause/Resume, Run now, cap controls, results and Undo. Non-quiet run notifications link from Inbox and Today; opening a retained conversation reads its own notifications. Legacy responsibility UI remains pending. See the [explicit exclusions](superpowers/specs/2026-10-14-persistent-agents-design.md#out-of-scope-recorded-for-future-work).

POST `/api/v1/responsibilities` takes operationId, title (trimmed 1–160), goal (trimmed 1–4000) and optional owner sensitivity (unlabeled default). Source is server-assigned owner-entered; status starts paused/version 1. Labels retain the complete unique history of owner-applied labels. Attachments, refs/source manifests, providers, tools, budgets, client status/source/labels and arbitrary execution settings are rejected. Goal text is data, never executable code or an instruction granting authority.

GET `/:id` returns owned current fields, including a deletion tombstone. PUT `/:id` replaces owner fields with expectedVersion/operationId, accumulates labels, increments version and cancels every blocked run with source-changed. There are no old goal-text snapshots; run hashes identify admitted inputs but cannot reconstruct prior text. UI inspection must distinguish current text/version from unavailable historical text.

POST `/:id/resume` moves paused to active. POST `/:id/pause` moves active to paused and cancels blocked runs. POST `/:id/cancel` closes paused/active records permanently and cancels blocked runs. DELETE `/:id` retains a cancelled tombstone and cancels blocked runs; an already cancelled record may be deleted. Every operation takes operationId/expectedVersion and advances the parent version. Cancelled/deleted records cannot resume or be edited; there is no restore. Resume never revives cancelled runs. Owner create of a new record is deliberate, not an automatic retry.

Active means scheduling/manual placeholder requests are permitted, not an agent is running. Source text provenance, provider routing, permissions, budgets and final action capability remain unverified. Responsibility goals do not change planner/study goals, settings, memory or email authority.

Mutations store metadata-only parent receipts `{ responsibility: { id, version, status, deletedAt } }`; fetch detail after saving. Successful exact retries return historical metadata without reapplying changes, even after pause/cancel/delete/restart. Changed successful operation IDs conflict. Ownership/session authorization applies before retries. Refresh current detail/run state after an old receipt. Row locks and receipts serialize lifecycle changes; failures roll back root/run/activity changes together.

Delete hides a responsibility and retains its current goal/title/labels/history/export; it is not memory forgetting or permanent erasure. Explain retained content when offering deletion. Old database pages/backups/downloads and user copies have separate retention limits; no permanent erase policy is implemented.

GET `/api/v1/responsibilities` supports status=paused/active/cancelled/all (all default), deleted=false/true/all (false default), limit 1–100 (25 default), paired after/expectedCursorVersion and nextAfter `{ id, version }` or null. UUID-ascending summaries include title/metadata but omit goal. Cursors must be owned/filter-eligible (404 otherwise), and eligible changed versions conflict (409). Each page is a session-rechecked consistent snapshot, not frozen multi-page history. Reset cursors when changing filters and guard delayed reads.

## Milestone 2: UTC review schedules and explicit due admission

GET `/:id/schedule` returns the owned schedule or null. PUT takes operationId, expectedVersion (parent content/lifecycle version), and schedule `{ startsAt, intervalMinutes }` or null. startsAt is a UTC Z instant; null interval means one-time. Recurrence uses a constant interval of 15–10080 minutes. It is elapsed UTC time, not a local calendar/cron rule; 1440 minutes may shift local clock time across DST. Local daily/weekly rules are implemented through the separate [local schedule endpoint](responsibility-local-schedules.md); this endpoint retains constant UTC cadence.

Set/replace increments the parent and existing schedule versions, resets nextDueAt to startsAt and cancels blocked runs with schedule-changed. Clear increments versions, sets schedule deletedAt/nextDueAt null and retains prior cadence metadata. Re-adding advances its version instead of erasing history. Schedule operational advancement changes only schedule.version, not the parent content version. A finished one-time schedule has nextDueAt null and no deletion tombstone. Pausing/cancelling/deleting excludes its schedule from due previews; resume exposes overdue scheduling again without silently admitting it.

GET `/api/v1/responsibilities/due` returns asOf (server UTC time), full dueCount, metadata-only items `{ id, version, title, scheduleVersion, nextDueAt }`, nextAfter `{ id, version, scheduleVersion }` or null, and executionEnabled=false. Limit 1–100/default 25, UUID ordering, paired after/expectedCursorVersion/expectedScheduleVersion. Only active, nondeleted parents with an active pending schedule due at asOf are included. Preview is read-only and neither creates runs nor advances schedules. Counts ignore pages; changed eligible parent/schedule versions conflict, and missing/ineligible/foreign anchors return 404.

POST `/api/v1/responsibilities/admit-due` takes operationId and 1–25 unique selected items `{ id, expectedVersion, expectedScheduleVersion }`. It uses server time captured after canonical UUID parent locks, checks every owned active parent/schedule/version and rejects future/exhausted/cleared schedules. The selected batch commits atomically or rolls back all runs, activities, due pointers and the receipt. Case variants of the same UUID are duplicates; canonical lock order avoids opposing batch deadlocks. No client clock or filter-wide implicit selection authorizes admission.

Admission creates one blocked run for each selected earliest pending slot. One-time nextDueAt becomes null. Repeating schedules count missed intervals and advance nextDueAt to the first cadence slot strictly after server now, creating no backlog fan-out. skippedIntervals records the coalesced extra missed slots, not completed work. Constant cadence retains startsAt alignment. Existing slot uniqueness persists through schedule clear/replacement and source/lifecycle changes; reusing an admitted slot returns DUE_ALREADY_ADMITTED, requiring a deliberate new start time. It never resets or revives a prior run.

Exact successful batch retries return historical run metadata without advancing the pointer again. Distinct stale requests conflict; schedules never transmit anything. There is no automatic/background admission or provider queue. A future worker must add leases, bounded admission, stop rechecks, provenance/routing/permissions/budget enforcement and uncertainty handling before unattended execution.

Batch results follow canonical responsibility UUID order; match runs by responsibilityId, not the submitted selection position.

## Milestone 3: durable blocked runs, dismissal and activity

The subsequent [global review inbox](responsibility-inbox.md) adds chronological current-source inspection, full attention counts and atomic explicit selected dismissal. Existing per-parent history/dismissal remains unchanged.

POST `/:id/runs` takes operationId/expectedVersion (parent) and creates an owner-requested manual blocked placeholder only while active. A deliberate new operation may create another manual placeholder. GET `/:id/runs` pages UUID-ascending metadata with limit/paired after/expectedCursorVersion; GET `/:id/runs/:runId` requires owned same-parent identity. Responses always include executionEnabled=false. Runs omit title/goal, prompts, results, provider credentials and model/tool responses.

Run fields: id, responsibilityId, admitted responsibilityVersion, independent version, trigger=manual/schedule, scheduledFor/scheduleVersion (null for manual), skippedIntervals, private integrity inputHash, captured owner labels, status=blocked/cancelled, cancelReason, createdAt/cancelledAt. blocked does not mean dispatched; there is no running/completed/success result. The hash is neither approval nor verified provenance. Captured labels alone cannot discard later owner label history: future disclosure must recheck the current owned source/version/labels and provenance. Label/goal edits currently cancel blocked runs rather than executing stale context.

POST `/:id/runs/:runId/dismiss` takes operationId/expectedVersion (run version, not parent), changes blocked to cancelled with owner-dismissed, increments run version and appends activity. It changes neither parent version nor schedule pointer. Pause/cancel/delete/goal edits/schedule changes cancel blocked runs with their reason and version+1; cancelled history remains. No retry, dispatch, confirm-success or result endpoint exists. Historical create/admit receipts can still report blocked after cancellation; reload detail/history before displaying current state.

GET `/:id/activity` returns metadata-only immutable activities by UUID, limit 1–100/default 25, optional owned same-parent after and nextAfter UUID/null. Fields: id, responsibilityId, responsibilityVersion, kind, optional runId and createdAt. Kinds record create/update/resume/pause/cancel/delete, schedule set/clear, run create/dismiss and aggregate run cancellation. Activity never copies private goal text and is not a provider execution receipt. UUID order is pagination order, not chronological event order; use timestamps for display and do not infer before/after text or total execution from events. No update/delete activity API exists.

Owned composite foreign keys bind schedules/runs to parents and activity run references to the same parent. SQL checks constrain lifecycle, schedule ranges, terminal timestamps/reasons and trigger fields. One slot per owned parent/time is durable. Export adds default-empty responsibilities, responsibilitySchedules, responsibilityRuns and responsibilityActivities to format v1; it includes root tombstones/private current text, cleared/exhausted schedules, run cancellation and activity. Existing row/size bounds reject partial/oversized exports. No import, offline outbox/cache, UI or model context reference is added.

## Validation and pending gates

All 15 focused synthetic tests passed, including the consumed-slot/case-duplicate regression. Checks cover strict fields/blocked defaults, ownership/session/origin isolation, exact/concurrent/historical receipts, labels, lifecycle invalidation, one-time/coalesced cadence, future/stale/atomic selected admission, opposing batches, dismissal/paging/cursors, forced rollback/SQL relationships, export compatibility, populated migrations and persisted restart. Fetch is forbidden and databases are isolated in memory or `.artifacts`; no owner database or real provider is accessed.

Optional standard PostgreSQL coverage adds duplicate parent creation/admission, lifecycle cancellation and export in the disposable schema; it remains unverified locally while TEST_DATABASE_URL is unset. Full npm run check passed lint, strict types, formatting, production builds and 302 API/client tests; one optional standard PostgreSQL test was skipped. Browser tests were not rerun because UI/authentication-layer code was unchanged. No owner database reads/resets, real providers, paid AI or device tests occurred. UI controls, background scheduling/leases, verified context/retrieval and policy/budget enforcement, live executor/provider reconciliation, real results, planner actions, email sends and MCP remain pending. These three milestones do not establish autonomous agents or full reference parity.
