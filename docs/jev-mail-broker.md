# Jev mail broker foundation (J1/J2)

Historical J1/J2 foundation receipt: current owner-ask/agent integration and changed runtime behavior are documented in [J3 workflow](jev-mail-workflow.md). Statements below about disconnected dispatch and pending J3 describe the foundation slice before J3.

Implemented in development on `ai/jev-broker-foundation`; not deployed or connected to live owner asks/scheduled agents. J3 owns workflow integration, downstream transmission and conversation lineage; J4 owns settings controls, old Use mail migration and staged acceptance. Existing agent mail behavior is unchanged in this foundation release. The [delivery plan](jev-mail-broker-plan.md) remains the product contract.

## Owner contracts

- `GET /api/v1/mail-broker/grants` lists owned grants. `PUT /api/v1/mail-broker/grants/:target` saves a grant for `owner` or an owned agent UUID. Body: `{operationId, expectedVersion, enabled, scope: {connectorIds, receivedAfter, receivedBefore}}`. Creation expects version zero; updates increment it. Receipt replay is idempotent and current session authorization is rechecked. Dates are inclusive after/exclusive before. The scope requires unique owned connectors; enabled grants require active connectors. Unknown fields, folder and unread filters are rejected. Disabling remains possible after a connector is revoked.
- `GET /api/v1/mail-broker/readiness` reports separate Jev blockers, downstream readiness, provider revision and consent version. `dispatchConnectedToAgents` is always false in this slice. A ready adapter is not evidence of account setup or live mail acceptance.
- Shared contracts define requests, grants, result messages and coverage. Internal requests have at most 500 candidates and 50 results. Coverage distinguishes locally inspected records, eligible records and Jev-judged records, imported scope, per-connector last upload seen and import start dates, clipping and stop reason; external completeness remains unverified.

No public execution, candidate-list or arbitrary-message-read route exists. Owner Mail browsing continues through its existing routes. J1/J2 tests call the internal service with synthetic contexts; a model cannot supply owner IDs, labels, budget bounds or lease evidence.

## Selection and receipts

Migration 064 adds owner/agent grants, retrieval snapshots and batch receipts. Migration 065 adds selected IDs and threshold revision. No legacy mail consent or source provenance is invented. Grants reference owned identities; receipts store private digests, versions, labels, cursors, decisions and accounting metadata, never intent/body/subject text or credentials.

An internal retrieval snapshots a deterministic newest-first imported window (received timestamp then UUID), binding grant revision, request digest, server-supplied request labels, downstream destination/settings, budget version, deadline and optional agent/run lease plus goal digest. Both message and connector labels must be allowed at Jev and the downstream destination before a candidate is exposed. Restricted labels, revoked connectors and anything lacking `message-body-v1` origin are excluded. Personal requires both Jev routing approval and existing downstream Personal permission. Request labels pass the same intersection. Agent inherited labels must remain unlabeled, preserving current runtime restrictions.

Pages have up to 25 candidates, dynamically split to fit 20 KiB UTF-8 and profile character bounds. Jev sees headers and a plain-text excerpt of at most 1,000 Unicode code points, with clipping explicit. Each candidate gets its own comparable Score against `mail-relevance-v1`; the request and mail are data, not permission/rubric instructions. The initial `synthetic-threshold-v1` selects score at least 2 with at least 0.75 probability on directly useful/central evidence. These thresholds have synthetic coverage, not private-mail calibration. Jev never returns application message IDs: server keys bind answers to the expected candidates.

Full original content hashes, message/connector versions, labels, grants, destinations, consent, operator verification, budget policy and agent lease are rechecked before transport. The exact serialized envelope is privately bound to its durable batch. Missing/foreign/duplicate answers, duplicate JSON keys, changed model, nonfinite/inconsistent scores, wrong legends and invalid distributions fail closed. Valid usage can settle even when judgments are invalid; missing or untrustworthy usage retains an uncertain hold. Stored selections reject changed rubric, bounds or threshold revisions; decisions retain the score probabilities as metadata.

Internal selection copies original messages, with bodies capped at 6,000 UTF-16 code units without splitting a surrogate pair, at most 50 messages and 128 KiB serialized message-array bytes. It rechecks all evaluated dependencies, including losers affecting ranking, and refuses source changes. IDs and coverage are checkpointed without copied text. This preview is not downstream send authorization. J3 must bind complete selection dependencies, grant revocation and request labels into actual downstream envelopes and later conversation history, then recheck at transmission.

Current manifest capacity limits a snapshot to 350 eligible candidates, even if 500 local records were inspected. Coverage reports the lineage stop rather than dropping dependencies. Pages continue only inside that snapshot. Reaching the scan/lineage cap reports partial coverage; continuing into older imported windows is J3 work. No external inbox completeness is inferred. Imported connector freshness UI is J4 work.

## Provider and accounting gates

TypeSafe uses a server-declared `AI_PROVIDER_PROFILES` entry with alias `jev-mail`, adapter `typesafe`, a pinned `jev-x.y.z` model, a server-held `AI_SECRET_*` credential, input/output bounds, expiring pricing and versioned retention disclosure. The fixed endpoint is `https://api.typesafe.ai/v1/systemone`; callers cannot change it. Owner consent uses existing provider-consent routes and binds the public profile revision; Jev must also appear in the allowed routing policy for every source/request label. OpenRouter approval never approves TypeSafe. The receiving OpenRouter model is unchanged.

`TYPESAFE_VERIFICATION` is optional server JSON; absent or stale evidence blocks dispatch. Its fields are `revision`, `profileRevision`, `expiresAt`, `accountTermsZeroRetention: true`, `completeEnvelopeTokenBound: true`, `authoritativeUsageBilling: true`, `envelopeByteLimit` (1,024-20,480) and `inputTokenUpperBound` (1-32,000). These are operator attestations backed by actual account/billing/token-bound evidence, not a setup shortcut. The profile quote must cover that complete-envelope token upper bound. This adapter currently requires zero-priced output tokens; different billing needs a new verified output bound. Do not populate this from synthetic tests, an API key, or public marketing claims. Change the evidence revision when any account, credential account identity or verification changes; expired evidence or a changed profile requires fresh verification and consent. TypeSafe's public docs describe enterprise ZDR; actual account terms and full-envelope billing still need verification before enabling real disclosure.

Before a Jev call, the shared owner budget lock admits its full quoted worst case and one downstream worst-case hold for the same logical request. Every batch plus that downstream allowance must fit the saved per-request limit; both count toward the unchanged owner monthly and agent caps. Ordinary live agent admissions and allowance displays use the same combined reservation set. The server supplies downstream bounds; J3 must compute them from the actual downstream envelope/quote and consume this reservation rather than create a second hold. An abandoned unsent downstream reservation has an internal release helper; it cannot release uncertain Jev charges. There is no HTTP usage-confirmation or retry override.

Batches become uncertain durably before transport. A second worker, restart or lost response returns the receipt and never resends. Successful usage settles using the verified configured rates with integer upward rounding. Transport errors, non-success HTTP responses (including 429), malformed usage, timeouts and missing usage keep holds. Failed final guards release unsent reservations; there is no fallback. HTTP has no redirects, retries or long-context header, a 20-second deadline and 128 KiB response bound. An agent run allows at most two retrievals; paused agents may finish a currently leased run, but changed goals/labels, lost lease, revoked grants or deadline expiry stop new admissions.

## Verification and remaining work

Routine tests use isolated synthetic mail and fake transport, including stable ordering, over-500/over-50 bounds, two-hop labels, unsafe provenance, Unicode splitting, malformed answers, both budget levels, competing dispatch claims, changed context before send and actual database close/reopen. The same suite runs in a disposable PostgreSQL schema when `TEST_DATABASE_URL` is provided; CI includes it in the PostgreSQL job. No real provider calls, owner mailbox reads, paid requests or deployment were used.

J3 must connect both owner asks and agents, replace raw mail search/read without fallback, transfer downstream holds safely, add complete broker-derived conversation lineage/revocation, continue older windows and integrate run recovery/status receipts. J4 adds settings, reliable imported freshness/coverage displays, migration of existing mail switches, keyboard/tap/320px verification and staged deployment. These remain pending; neither the existing Use mail flag nor these backend grants enables Jev disclosure today.

API shape, Score semantics and model/retention research rechecked 2026-10-15 against the [API reference](https://docs.typesafe.ai/api), [Score](https://docs.typesafe.ai/primitives/score), [models](https://docs.typesafe.ai/models) and [selection cookbook](https://docs.typesafe.ai/cookbooks/classifying_rag_passages). Vendor docs do not prove the owner's account terms or private-mail quality.

Local validation: `npm run check` passed lint, all workspace types, 796 unit/API/client tests (three optional PostgreSQL cases skipped locally), formatting and production builds. Sequential `npm run test:e2e` passed all 156 isolated Chromium cases. Remote Linux/Windows/PostgreSQL CI remains a merge gate; deployment and owner live acceptance remain separate.
